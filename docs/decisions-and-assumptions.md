# Решения и допущения

## Что я решил сам там, где ТЗ неоднозначно

**Роли и доступ**
1. **Исполнитель при создании задачи обязателен.** В ТЗ сказано «назначает исполнителя», но задачу без исполнителя никто не смог бы взять в работу. Назначить можно только пользователя с ролью «исполнитель», это проверяет база.
2. **Принять или вернуть задачу может любой постановщик, а не только её автор.** ТЗ говорит, что постановщиков несколько, и не привязывает приёмку к автору.
3. **В карточке объекта исполнитель видит только свои задачи**, а не задачи коллег. Так следует из «видит только свои задачи». Из-за этого объект исчезает из его списка, если все его задачи на нём переназначили.
4. **Исполнитель видит постановщиков, но не других исполнителей.** Постановщики нужны для полей «автор» и «кто принял» в истории. Остальные исполнители ему не нужны, и база их не показывает.
5. **Профили (роли) создаёт администратор в базе**, а не пользователь при входе. Пользователь, у которого есть логин, но нет профиля, ничего не видит и ничего не может. Роль нельзя поменять через API.

**Задачи и статусы**
6. **Создание задачи записывается в историю** как «— → Новая». Это тоже смена статуса по таблице переходов из ТЗ.
7. **Комментарий обязателен только при возврате на доработку.** В остальных переходах он необязателен. Комментарий из одних пробелов, табуляций или переводов строк считается пустым (на это нашёлся баг в первой версии, он исправлен). Максимальная длина 2000 символов.
8. **Постановщик не может поставить статус напрямую**, ни «Принята», ни любой другой. Статус меняется только по таблице переходов. Это же верно для автора и даты создания.
9. **«Принята» — конечный статус.** ТЗ не описывает переходов из него, поэтому их нет.
10. **Постановщик может редактировать название, описание, объект и исполнителя задачи в любом статусе.** Смена исполнителя в историю не пишется, потому что ТЗ требует хранить смены статуса. Прежний исполнитель сразу теряет доступ к задаче и её истории.
11. **Справочник переходов лежит в таблице базы (`task_transitions`).** Это копия таблицы из ТЗ. Интерфейс берёт из неё список доступных кнопок, поэтому правила записаны в одном месте.

**Удаление**
12. **Постановщик может удалять задачи и объекты.** Удаление объекта удаляет его задачи. История задачи удаляется только вместе с задачей, напрямую стереть или изменить её нельзя никому. Это компромисс между «постановщик удаляет задачи» и «историю нельзя удалить». Строже было бы мягкое удаление с пометкой, но в рамках 2–3 часов я его не делал.

**Прочее**
13. В базе хранятся английские коды статусов (`in_review`), а русские названия подставляет интерфейс.
14. Бесплатный тариф Supabase **ставит проект на паузу после 7 дней без активности**. Если ссылку откроют после паузы, нужно нажать «Restore project» в панели Supabase (около 30 секунд).
15. **URL проекта и publishable key лежат в `.github/workflows/deploy.yml`** (для сборки сайта). Это публичные значения: ключ по замыслу Supabase безопасен для браузера и всё равно попадает в код сайта, а доступ к данным ограничивают правила в базе. Секретных ключей (`service_role`, `sb_secret_…`) в репозитории нет.
16. **Адреса страниц вида `/#/tasks/…`** (HashRouter): так прямые ссылки и обновление страницы работают на статическом хостинге без настройки сервера. Сайт публикуется на GitHub Pages.

## Что не успел или сделал не до конца

- **Нет автотестов фронтенда.** База покрыта 36 автотестами, интерфейс проверен браузерным прогоном с подменой ответов сервера и вручную.
- **Нет пагинации и поиска.** Есть только фильтр по статусу в «Мои задачи». Для нескольких десятков задач этого достаточно, для тысяч нет.
- **Нет управления пользователями в интерфейсе** (создание, смена пароля, отключение). Пользователей создают вручную в Supabase, как разрешено в ТЗ.
- **Нет уведомлений и автообновления.** Чтобы увидеть изменения других пользователей, нужно обновить страницу.
- **Нет журнала удалений и мягкого удаления** (см. п. 12).
- **Смена исполнителя и редактирование полей задачи не журналируются** (см. п. 10).
- **Параллельные нажатия** защищены блокировкой строки в базе (два одновременных перехода из одного статуса не пройдут оба), но под нагрузкой я это не проверял.
- **Защита от подбора пароля и частых запросов** стандартная, из Supabase Auth, своих ограничений я не добавлял.
- Дизайн минимальный: стандартные компоненты Mantine, без оформления под бренд.
